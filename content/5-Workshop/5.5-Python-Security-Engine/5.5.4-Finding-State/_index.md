### Overview

After Security Checks are performed, the results need to be represented using a consistent data structure so that the Security Engine can continue processing them.

In this project, this functionality is organized as follows:

~~~text
python/

├── models/
│   └── finding.py
│
└── state_loader.py
~~~

`finding.py` focuses on the **Security Finding** model, while `state_loader.py` is responsible for loading and processing stored security state information.

### 1. Security Finding

File:

~~~text
python/models/finding.py
~~~

defines the data structure of a **Finding**.

A Finding represents an issue or result identified during a security check.

The general workflow is:

~~~text
Security Check

      ↓

   Finding

      ↓

Security Engine
~~~

![ASAU](/images/01/image_248.png)

### 2. Role of Finding

Finding provides a standardized representation for results generated by different Security Checks.

For example:

~~~text
SSH Check

    ↓

 Finding

    ↑

    |

Firewall Check
~~~

Instead of having each security check return a different data structure, the results can be represented using the Finding model so that subsequent components can process them consistently.

### 3. Security State

In addition to Finding, the project contains:

~~~text
python/state_loader.py
~~~

This component is related to handling the security state of the system.

The project stores state information under:

~~~text
output/security_state/

├── managed-01.json
└── managed-02.json
~~~

Each state file corresponds to a Managed Node.

![ASAU](/images/01/image_249.png)

### 4. `state_loader.py`

File:

~~~text
python/state_loader.py
~~~

is used to work with security state data stored by the system.

The general workflow is:

~~~text
Security State

      ↓

state_loader.py

      ↓

Python Security Engine
~~~

![ASAU](/images/01/image_250.png)

### 5. Finding and Security State

Finding and State serve different purposes:

~~~text
Finding

  ↓

Detected result / security issue

State

  ↓

Stored security status of a Managed Node
~~~

Their relationship can be illustrated as:

~~~text
Managed Node

      ↓

Security Checks

      ↓

Finding

      ↓

Security Engine

      ↓

Security State
~~~

Finding represents the result of a security check, while State preserves security information for subsequent processing.

### 6. Relationship with Output

The security state of the Managed Nodes is stored under:

~~~text
output/security_state/

├── managed-01.json
└── managed-02.json
~~~

The project also stores generated reports under:

~~~text
output/reports/

├── history/
└── latest.json
~~~

Therefore, security-related data is organized into two main outputs:

~~~text
Python Security Engine

        |

        +── Security State
        |       ↓
        |   security_state/
        |
        └── Report
                ↓
             reports/
~~~

![ASAU](/images/01/image_251.png)

![ASAU](/images/01/image_252.png)

### 7. Overall Workflow

The overall workflow can be represented as:

~~~text
                  Managed Nodes

                       ↓

                Security Checks

                       ↓

                    Finding

                       ↓

                Security Engine

                       |

                +------+------+
                |             |
                ↓             ↓

              State         Report
                |             |
                ↓             ↓

        security_state/     reports/
~~~

Security Checks generate Findings, the Security Engine processes the results, and the system stores the corresponding security state or generates reports.

### Result

After completing the Finding and State components, the project has a mechanism for standardizing and storing security results:

~~~text
Security Check

      ↓

   Finding

      ↓

Security Engine

      ↓

+-----+------+
|            |
↓            ↓

State       Report
~~~

This structure allows security results to be reused by subsequent components for **Reporting** and **Automated Remediation**.
